# From a study to a submission or revision

**Identify the deliverable.** Use the author's template, bibliography, existing files and target instructions. Check current limits, anonymisation, required supplementary files, and whether references count toward the page limit. State any constraints you could not verify. For initial submission, keep editable source and its final render. For resubmission, preserve the previous submitted bytes and work on a new version. Do not upload a manuscript as part of preparing one.

**Choose the evidence check by the origin of the work, not the file extension.**

| Starting material | What to check and hand over |
|---|---|
| Author-supplied Word or PDF, existing evidence answers the concern | Keep the original. Read the cited source or result, revise a separate file and check its rendered pages against the evidence and reply. Report which historical records were supplied or missing and what that limits. A current revision does not require a new experiment, `research/plan.json` or `research/run.json`. |
| Outside manuscript plus a new formal comparison | Freeze and run the comparison in its own supplement. Run `python3 "$KIT/ai4sci.py" audit "$SUPPLEMENT"` there. In the handoff distinguish the supplement's findings from the original results. Review the exact revised outside manuscript and reply as above. The supplement audit covers only the new work. |
| Formal Word or PDF submission from a study conducted with this kit | Keep the study's frozen plan, run, evidence ledger and current delivery records. Inspect the rendered pages and run `python3 "$KIT/ai4sci.py" audit --submission "$STUDY"`. Both the native evidence audit and the package check are required. |

**Use the format people will edit.** For Word, work on the `.docx` and preserve styles, figures, captions and requested tracked changes. For LaTeX, use the supplied class and reference files, build from a clean directory, capture the build command, inspect unresolved references and read the resulting PDF. Render the actual Word file in a compatible viewer if Word is requested. A conversion of the Markdown draft is not a visual check of an edited Word file. For a spreadsheet supplement, check the delivered rows, units and formulas against the measured outputs. Return precise paths. When a template or renderer is unavailable, deliver what exists and identify the unverified step.

**Triage the review before writing a response.** Keep each original comment and distinguish separate concerns within it. For each, record the scientific question and choose a disposition: point to existing evidence, run a discriminating supplemental test, narrow or withdraw a claim, or disagree with evidence. State where the reply and final paper will change. Combine duplicate requests, but preserve the link back to each reviewer. If the user asked only for a response strategy, stop here.

**Keep the thread across rounds.** If a later reviewer challenges an answer that looked complete, reopen the same issue and keep the old comment, reply and manuscript. Give genuinely new questions new issue IDs. Where reviewers ask for opposite changes, explain how the evidence bears on each request and what the paper now says. Use the optional [review-round trail](../../../checks/rounds.md) for multi-reviewer or multi-round revisions. The [two-round demonstrator](../../../examples/review-rounds/) shows an author retaining a challenged baseline while revising a different claim. A single draft or an advice request needs none of these extra files.

**Start from the evidence the author has.** For a study run with this workflow, verify the digests of the original records it promised. For an outside manuscript, preserve the supplied manuscript bytes, reviewer comment and locator, and available materials with their provenance. State which historical records are unavailable rather than filling them in. If an existing figure, table or output answers the concern, cite it in the reply without freezing a plan or running a test. Keep supported wording and qualify or remove unsupported assertions in the revision.

**Run work that could change the answer.** If a new analysis is needed, use the [experiment stage](../../ai4sci-experiment/SKILL.md) to freeze the cheapest discriminating comparison in a separate supplement before measuring it. Audit the supplement, not the outside study. Label reuse of a previously inspected holdout as sensitivity analysis. If a necessary datum is missing, name it and explain what cannot be tested. Distinguish a missing historical receipt from a missing observation. Report an uninformative result as such.

**Close the issue in the delivered version.** Update the affected results, figures, abstract and interpretation, not just the limitation paragraph. In the response quote the concern, state what was done and what it showed, and identify the exact changed section, figure or table. Distinguish work completed from future work. Preserve unrelated changes made by coauthors. Before handing off, let someone other than the writer inspect the actual file and the reply together. If only the author is available, label it self-review.

**Check the requested file.** For a revised Markdown manuscript, have an independent reader open the exact `.md` being delivered and check it against the reply and cited evidence, including repeated claims in the abstract and conclusion. Record the file checked and any unresolved claims. Label self-review if no independent reader is available. Markdown delivery does not require `submission.json` or a Word/PDF rendering check.

For **every Word or PDF handoff**, open the exact revised PDF or render the actual edited DOCX in a compatible viewer. Read the changed passage, abstract, conclusion, figures and captions alongside the response and the cited evidence. Record the exact files or digests, reviewer, inspection method, findings and unresolved points. A missing renderer leaves the page review pending. Do not mark the package approved on extracted text alone.

For an outside revision, a direct evidence and page review is sufficient when the supplied materials support the claims. If current `research/paper.md`, `research/claims.json` and a [`research/submission.json` package](../../../checks/submission.md) with its dated review already exist or have been prepared for this delivery, `python3 "$KIT/checks/submission.py" "$STUDY"` can additionally diagnose file identity and extracted claim text. Its result describes only the current package. It does not verify the historical study, judge the evidence or replace the page review. Do not create historical plan or run records to obtain an audit status. For a native submission the standalone diagnostic does not replace `audit --submission`.

The issue-by-issue responses and follow-up rounds draw on [ARIS's rebuttal workflow, especially Phase 8](https://github.com/wanshuiyin/Auto-claude-code-research-in-sleep/blob/4ba94ae2a1c1fbbb14858750dd8764cabf6c28bd/skills/rebuttal/SKILL.md#phase-8-follow-up-rounds). The compile and review cycle draws on [ARIS's paper-writing workflow](https://github.com/wanshuiyin/Auto-claude-code-research-in-sleep/blob/4ba94ae2a1c1fbbb14858750dd8764cabf6c28bd/skills/paper-writing/SKILL.md). The version and evidence checks here are this kit's own implementation.
