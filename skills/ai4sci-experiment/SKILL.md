# From hypothesis to results

Use this stage for benign computational research. For design only, return the proposed comparison and stop before execution. Do not design or run exploits or experiments that facilitate harmful biological or physical activities.

## Freeze the comparison

Name the claim, strongest feasible baseline, unit of analysis, inputs available at prediction time and what result would count against the claim. For reproduction, locate the reference result and distinguish matched conditions from substitutions. Fix the primary metric, units and direction, uncertainty estimate (or deterministic rationale), consequential effect size or tolerance, and split or analytic reference. Identify observations already seen and who or what had access to the held-out outcomes.

Before formal evaluation, use the [plan template](../../templates/plan.json) and [file contract](../../checks/contract.md) to write `research/plan.json`. For finite planned cells, put `required_observations` on the corresponding criterion; add `bounds` for a numeric prediction. Declare `matched_conditions` for quantities meant to stay fixed across arms. Set a study-specific ceiling on trials, time or compute, including repairs; reserve enough for the decisive comparison. State when to stop for adequate evidence, an informative miss, an unavailable input or an inconclusive result. From the checkout, `python3 ai4sci.py freeze PROJECT` records the raw plan digest, not an external timestamp.

## Run in stages; spend the next trial on a disagreement

1. **Establish the baseline.** Pilot on development inputs to check units, leakage, scoring and runtime. Reproduce the baseline on the intended comparison set before interpreting a change. Keep splits, preprocessing, information access and resource allowances equal between arms except for the intended contrast. Record what actually ran on this host or remote job, not the requested settings alone.
2. **Read the evidence before deciding what comes next.** Compare the observed difference and its uncertainty to the baseline and frozen prediction. Point to the output row or diagnostic that is still ambiguous. Give two plausible explanations and choose the cheapest control on which their predictions differ. For example, suppose a forecast beats the baseline on familiar meters. A transferable pattern predicts some gain on unseen meters; memorizing meter identities predicts none. Compare both methods on a meter-disjoint development split at the same forecast horizon and training budget. Losing the gain would narrow the claim, not prove memorization. If the uncertainty spans both predictions, report that the contrast did not decide between them.
3. **Keep the decision trace short.** In the study notes, record the observed comparison and locator, the rival predictions, the selected next test and remaining budget **before** seeing its result. Afterwards append the outcome, including null, adverse or inconclusive findings, and the decision to continue or stop. Compare alternatives for one decision against the same baseline; carry a result forward only if the next question depends on it. Keep all attempts. Label data-inspired follow-ups exploratory; leave the original criteria intact. Stop when the first comparison answers the question.
4. **Separate technical failure from scientific outcome.** If a crash prevents measurement, retain the failing command, exit, logs and cost. Repair the diagnosed cause only within the declared allowance, as a new attempt under the same comparison. A measured failure to meet a threshold is a completed result, not permission to retry. Stop at the cap or when no affordable contrast would change the inference; identify untested criteria and what would be required to resolve them.
5. **Confirm at the right level.** Lock the selected method and rule before using untouched evaluation units independent at the level the claim concerns, or a genuinely independent replication. For a simulation claim about random draws, use a prespecified independent draw stream. Reusing a holdout that informed selection, even with a different seed, metric or split of the same rows, is a **sensitivity analysis on reused data**, not fresh confirmation. Say what was reused and what changed; narrow the conclusion if fresh evidence is unavailable. Repeating a deterministic calculation checks reproducibility, not population generalization.

## Preserve what the study established

Write `research/run.json` per the contract. For a completed comparison record `status: "completed"`, the actual `command`, `plan_sha256`, study-relative `outputs` (including every evidence CSV), and observed common `conditions` for each declared arm. Keep the input and code versions or checksums, effective environment, exit status and raw measurements. If using the output `sha256` map, hash **all** listed output files over their raw bytes. Use `failed` or `blocked` with a reason when the measurement could not be made. Never declare missing required observations completed. For table comparisons, align the full set of unique sample IDs and apply the prespecified tolerance; for cluster labels distinguish a permutation from a changed partition. See `python3 checks/compare.py --help` from the checkout.

**When a reviewer requests another test:** locate the affected criterion, claim and evidence. First see whether the original outputs already answer it; if so, point to them. If the request changes the comparison, threshold, data or analysis after seeing results, treat it as a **separate supplemental study**. Before any remedial work, record the original study location and SHA-256 digests over the original bytes of its plan, freeze record, run receipt, outputs, claim ledger and manuscript, plus any input or code on which the supplement depends. Keep the original files read-only. A missing or mismatched original is a provenance gap to resolve, not a reason to manufacture a receipt.

In a separate study directory, state the reviewer's objection, what was already seen, the changed comparison, rival predictions and the limit on attempts. Freeze the new plan there before the new analysis. Give an executor the bounded comparison and a checker its original locators, digests and new outputs; if working alone, label the check as such. Keep the supplement's run, outputs, claims and review there. Use supplement-local copies with verified digests for original evidence needed by its audit; the audit cannot follow evidence paths outside its study. Recheck the original digests and audit the supplement separately. Report the original and supplemental findings side by side: does the objection stand, narrow the claim, or remain unresolved? Do not replace the original plan, digest, receipt, measurements or conclusions, or refreeze them to make the new question look prospective.

For criterion-by-criterion checks, consult [criterion verification](references/autoscirub/criterion-level-verification.md) and [targeted revision](references/autoscirub/targeted-revision.md) under the local contract. [AIDE's search policy](https://github.com/WecoAI/aideml/blob/b39bb0e145e7785bcbc29e1b5d123f01d8f04c2c/aide/agent.py#L161-L192) distinguishes drafting, debugging and improving from a recorded result; here the next comparison is selected by its ability to distinguish explanations, not by score alone.
