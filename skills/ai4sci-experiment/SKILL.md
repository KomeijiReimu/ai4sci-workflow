# From hypothesis to results

Use this stage for benign computational research. For design only, return the proposed comparison and stop before execution. Do not design or run exploits or experiments that facilitate harmful biological or physical activities.

For a runnable package that another machine will execute, follow [remote package review](../ai4sci/references/remote-package.md) from design to handoff. When asked only to prepare it, skip the pilot and formal run on both machines. Keep the frozen design and unrun software distinct from measured results.

## Freeze the comparison

For a publication-oriented comparison, get the [scientific review of the design](../ai4sci/references/publication.md) before the formal run. Revisit the reviewer if an observed result changes the main scientific decision.

Name the claim, strongest feasible baseline, unit of analysis, inputs available at prediction time and what result would count against the claim. For reproduction, locate the reference result and distinguish matched conditions from substitutions. Fix the primary metric, units and direction, uncertainty estimate (or deterministic rationale), consequential effect size or tolerance, and split or analytic reference. Identify observations already seen and who or what had access to the held-out outcomes.

Before formal evaluation, use the [plan template](../../templates/plan.json) and [file contract](../../checks/contract.md) to write `research/plan.json`. For finite planned cells, put `required_observations` on the corresponding criterion and add `bounds` for a numeric prediction. Declare `matched_conditions` for quantities meant to stay fixed across arms. Set a study-specific ceiling on trials, time or compute, including repairs. Reserve enough for the decisive comparison. State when to stop for adequate evidence, an informative miss, an unavailable input or an inconclusive result. From the checkout, `python3 ai4sci.py freeze PROJECT` records the raw plan digest, not an external timestamp.

## Spend the next trial on a disagreement

1. **Establish the baseline.** Pilot on development inputs to check units, leakage, scoring and runtime. Reproduce the baseline on the intended comparison set before interpreting a change. Keep splits, preprocessing, information access and resource allowances equal between arms except for the intended contrast. Record what actually ran on this host or remote job, not the requested settings alone.
2. **Read the evidence before deciding what comes next.** Compare the observed difference and its uncertainty to the baseline and frozen prediction. Point to the output row or diagnostic that is still ambiguous. Give two plausible explanations and choose the cheapest control on which their predictions differ. For example, suppose a forecast beats the baseline on familiar meters. A transferable pattern predicts some gain on unseen meters. Memorizing meter identities predicts none. Compare both methods on a meter-disjoint development split at the same forecast horizon and training budget. Losing the gain would narrow the claim, not prove memorization. If the uncertainty spans both predictions, report that the contrast did not decide between them.
3. **Keep the decision trace short.** Before seeing a follow-up result, record the parent observation and locator, rival predictions, the selected test and remaining budget. Afterwards append the outcome, including null, adverse or inconclusive findings, and the decision to continue or stop. A simple comparison needs no new file. If alternatives compete for the next trial, use an [optional branch ledger](../../checks/branches.md). Give siblings the same measured parent. Start a later round from the selected child's actual settings and retain the other branches. The [encoding example](../../examples/branch-decision/) shows a losing sibling and a second round. Label data-inspired follow-ups exploratory and leave the original criteria intact. Stop when the first comparison answers the question.
4. **Separate technical failure from scientific outcome.** If a crash prevents measurement, retain the failing command, exit, logs and cost. Repair the diagnosed cause only within the declared allowance, as a new attempt under the same comparison. A measured failure to meet a threshold is a completed result, not permission to retry. Stop at the cap or when no affordable contrast would change the inference. Identify untested criteria and what would resolve them.
5. **Confirm at the right level.** Lock the selected method and rule before using untouched evaluation units independent at the level the claim concerns, or a genuinely independent replication. For a simulation claim about random draws, use a prespecified independent draw stream. Reusing a holdout that informed selection, even with a different seed, metric or split of the same rows, is a **sensitivity analysis on reused data**, not fresh confirmation. Say what was reused and what changed. Narrow the conclusion if fresh evidence is unavailable. Repeating a deterministic calculation checks reproducibility, not population generalization.

## Preserve what the study established

Write `research/run.json` per the contract. For a completed comparison record `status: "completed"`, the actual `command`, `plan_sha256`, study-relative `outputs` (including every evidence CSV), and observed common `conditions` for each declared arm. Keep the input and code versions or checksums, effective environment, exit status and raw measurements. If using the output `sha256` map, hash **all** listed output files over their raw bytes. Use `failed` or `blocked` with a reason when the measurement could not be made. Never declare missing required observations completed. For table comparisons, align the full set of unique sample IDs and apply the prespecified tolerance. For cluster labels distinguish a permutation from a changed partition. See `python3 checks/compare.py --help` from the checkout.

## Respond to a reviewer about an existing result

Preserve the original files read-only before revision. How to identify the starting evidence depends on where the study was done:

- **Study run with this workflow:** record the study location and verify SHA-256 digests over the original bytes of the records it promised: plan, freeze record, run receipt, outputs, claim ledger and manuscript, plus any review, inputs or code relied on. Flag a promised record that is missing or mismatched rather than replacing it with a newly made receipt.
- **Author's manuscript from outside this workflow:** preserve the version actually supplied (DOCX, TeX and accompanying files, PDF or other source), the reviewer's comment and its locator, and the supplied data, code and other supporting materials. Note their source, version if known, file digests and the passage or data rows at issue. Identify what was never recorded or was not supplied. Do not reconstruct a historical plan, freeze, run or ledger, ask the author to initialize the kit, or describe earlier choices as prospective.

First ask whether the existing evidence answers the objection. If so, cite its exact locator in the reply. No new run or freeze is needed. Retain supported claims and qualify or withdraw assertions the evidence does not support. An unrecorded historical decision limits what can be said about the original analysis without preventing a new test. If a missing datum is **needed to perform the test**, identify it and the comparison it blocks. Leave that question unresolved unless the datum becomes available.

For a new comparison, threshold or analysis, open a **separate supplemental study**. State the objection, what was already seen, rival predictions and limit on attempts. Freeze only that new plan, before measuring its outcome. Give the executor the bounded comparison and the checker its original locators, digests and new outputs. Label a self-check as such. Keep the supplement's run, outputs, claims and review there, with digest-verified local copies of any original evidence its audit must read. Recheck the source digests and audit only the supplement. Report what the original showed and what the new comparison adds or fails to resolve. The audit does not validate the retrospective study.

For criterion-by-criterion checks, consult [criterion verification](references/autoscirub/criterion-level-verification.md) and [targeted revision](references/autoscirub/targeted-revision.md). The branch ledger adapts those distinctions without running either search policy.
